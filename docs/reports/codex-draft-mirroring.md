# Server draft mirroring

Room v7 adds durable per-draft revisions, a stable random token, known server UID/UIDVALIDITY, an in-flight APPEND revision, and deletion tombstones. The v6→v7 migration preserves snooze and queues existing drafts. No public UI contract change or new dependency.

saveDraft keeps the editor path local and queues a network-constrained DraftMirrorWorker. Saves replace the pending per-account work and coalesce into the latest revision after two quiet seconds; network failures use WorkManager backoff (minimum ten seconds). Replacing work during an APPEND relies on the durable in-flight revision for recovery. Periodic and manual sync also process pending draft changes. Startup recovers pending work. Manual-only account settings do not suppress explicitly queued draft writes.

Each APPEND sets the Draft flag, X-Dot-Draft-Id, and a deterministic revision Message-ID. Retrying an unacknowledged APPEND searches those headers before writing again. The in-flight revision survives local edits, discard and process death. Replacing a revision deletes only its previously known UID, with UIDVALIDITY validation. UIDPLUS targets expunge; other servers only mark that copy deleted and never perform global expunge.

The local draft represents its known server copy once in the Drafts list. Other server drafts remain independently editable through existing negative message draft handles. Draft lists now enumerate individual remote drafts, preserving separate conflicts even when References group them in one conversation. External replacement/deletion removes a clean local copy; dirty local edits are uploaded as a new version and foreign server copies remain separate. UIDVALIDITY uncertainty preserves copies rather than risking deletion. Send/discard persist tombstones; undo-send restores and queues a draft revision.

A server with no discovered Drafts folder keeps local edits queued and reports the missing folder; no arbitrary folder is silently created. IMAP cannot provide exactly-once APPEND transactions across a client/server crash; deterministic revision lookup handles acknowledged visibility, but a server that accepts an APPEND then delays making it searchable can still expose a duplicate. Such unknown copies are preserved rather than deleted by a broad header match.
